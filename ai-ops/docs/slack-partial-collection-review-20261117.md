# 로그 부분 수집·Slack 결과 설명 코드 검토

## 문제와 변경

로그가 수집 상한에 도달하면 유효한 진단 줄까지 버리고, 현재 로그가 Pod 예산을 모두 소모하면 이전 컨테이너 로그를 조사하지 못했다. 기존 상한 안에서 현재/이전 로그 예산을 나누고, 완결된 줄을 별도 `-sample` 증거로 정규화한다. 원래 `missing/truncated` 증거는 남으므로 `complete`나 전체 정상 판정으로 승격하지 않는다.

Slack은 판정·현재 상태, 확보한 자료, 부족한 자료의 이유, 런북 출처, 추적 정보 순서로 회신한다. 빈 조회와 표본 없음은 정상이나 0%로 해석하지 않는다. 문서 ID·버전·전체 해시·절 위치는 유지한다. 개행 없는 마지막 줄은 보수적으로 제외하므로 정상 로그라도 마지막 미완결 줄이 표본에서 빠질 수 있다.

## 코드 검토

- 기존 원시/후보 바이트·줄 수·응답·총응답·시간 제한과 UID/컨테이너 재검증을 확인했다.
- 완결 줄의 무효 인코딩/시각과 초과 응답은 계속 거부한다. 원문 로그/예외를 Slack 설명에 복사하지 않고 고정된 어휘로 요약한다.
- 저장 bundle/audit/report 재조회와 해시 결합, 동일 채널/스레드, 권한 재검증, 출처 철회, 실행 불가 경계를 유지한다.
- 검토 보완: 배포 객체를 확보했다고 배포 이력까지 확보한 것처럼 보이지 않도록 `배포 정보`로 표시한다. 시간 범위 밖의 로그를 `CI 이력 없음`으로 설명하지 않도록 두 이유를 분리하고 회귀 시험을 추가했다.
- 변경 범위에서 추가 차단 결함은 발견하지 않았다. GitHub 사람 리뷰나 실환경 검증을 수행했다고 주장하지 않는다.

## 검증

합성 fixture만 사용했다. 관련 단위·통합 시험 140개와 아래 검사 4종이 통과했다.

- `check_task_service_local.py`
- `check_slack_adapter_local.py`
- `check_runbook_context_local.py`
- `check_request_workflow_local.py`

깨끗한 main 기반 worktree에서 전체 **1,189개 시험 통과(실패/오류/skip 0, 53.105초)**. 이전 1,195개 결과는 별도 Lease WIP 시험을 포함했고, 이번 검토는 그 7개를 제외하고 설명 회귀 시험 1개를 추가한 범위다. 이전 작업 폴더의 Lease WIP는 이 변경에 포함하지 않는다. 실제 Slack 호출·인프라 조회·배포·장애·복구 실행·유료 모델은 하지 않았다.

## 유지 조건과 후속

C-04 시작15초, 안내 후 최소120초/시작 후210초 리뷰, 소유원복240초, 독립원복300초, 회복관찰120초 및 승인·잠금·원복 코드/설정은 변경하지 않는다. 기존 수집 설정과 분석기 버전도 유지한다.

main 반영은 실환경 반영과 다르다. 이후 별도 배포 범위에서 검증 이미지를 연결하고 새 worker의 설정 로드·사용자 시작 조사 회신을 확인해야 한다. 이번 작업은 실습 재개나 C-04/C-05 완료가 아니다.
