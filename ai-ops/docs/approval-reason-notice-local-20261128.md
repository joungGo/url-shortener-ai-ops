# 승인 요청 거절 사유 안내 (WF11 후속 7) · 2026-11-28

상태: 로컬 구현과 시험만 했다. 실제 Slack 확인은 다음 설치의 S1에서 한다.

## 문제
- WF11 S1(2026-11-26)에서 요청자 본인 계획의 승인을 다른 스레드에서 요청했다. 일반 거절 문구(`UNAVAILABLE`)만 받아 무엇이 잘못됐는지 알 수 없었다([실행 기록](wf11-execution-20261126.md) 5번).
- 이전에는 모르는 hash, 다른 스레드, 다른 사건이 모두 같은 응답이었고, 시험으로 고정돼 있었다. 다른 사람 계획이 있는지 응답으로 알아낼 수 없게 하려는 것이다.

## 변경 (`recovery_approval_wiring.RecoveryApprovalService.request`)
| 순서 | 확인 | 실패 응답 |
|---|---|---|
| ① | 이 hash의 계획이 서명된 요청자 **본인 것**으로 정확히 1건 | 일반 거절(그대로) |
| ② | 계획과 같은 채널·스레드 | **`OTHER_THREAD`(새 문구)**: `plan-recovery` 회신이 달린 스레드에서 다시 보내라 |
| ③ | 계획과 같은 사건 | **`OTHER_EVENT`(새 문구)**: 계획 스레드에서 `this` 또는 계획 회신의 사건 참조로 다시 보내라 |

- 새 문구는 ①을 통과한 뒤에만 나온다. 요청자가 이미 아는 자기 계획이므로 새로 드러나는 정보가 없다.
- 모르는 hash, 다른 사람 계획, 모호한 계획은 같은 스레드·다른 스레드·다른 사건 모두 **같은 일반 거절**이다.
- 문구에는 채널·스레드·사건 ID와 hash를 넣지 않는다.
- 둘 다 다르면 스레드를 먼저 안내한다.
- 승인 장부는 열지 않고, 현재 상태 관측도 하지 않는다.
- 재시작 계획도 같은 확인을 거친 뒤 갈라지므로 같은 안내가 나온다.
- 승인 장부 단계의 `approval_unavailable`(승인자 아님, 보관 만료, 지원하지 않는 조치)은 그대로 일반 거절이다.

## 검증
- 시험(`test_recovery_approval_wiring.py`, `test_recovery_restart_wiring.py`)
  - 기존 "균일 응답" 시험을 나눴다: 모르는 hash와 다른 사람 계획(같은/다른 스레드, 다른 사건)은 응답이 글자까지 같다.
  - 본인 계획 + 다른 스레드 → 스레드 안내. ID·hash가 없고, 장부·관측 0, 계획 스레드에서는 그대로 열린다.
  - 본인 계획 + 다른 사건 → 사건 안내. 둘 다 다르면 스레드 안내가 먼저 나온다.
  - 재시작 계획 + 다른 스레드 → 스레드 안내, 재시작 장부·읽기 0.
- 결함 변형 10/10 검출(다른 사람 계획에 사유 노출, 요청자 확인 제거, 안내를 일반 거절로 되돌림, 확인 제거, 순서 바꿈, 문구에 ID 추가, 채널만 비교 등).
- 관련 시험 62개, 전체 시험 1967개 통과(skip 1). 저장소 경계 검사 통과.
