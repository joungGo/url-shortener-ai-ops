# WF-01 사건 ID·두 채널 연결·조사 시작 정책 계약

2026-11-18 KST · 설계 v1 · **문서 계약 완료; WF-02 코어 로컬 구현, 외부 연결·배포 미착수**. 기준 AI main36a55fd. [전체 계획](incident-workflow-and-improvement-plan-20261118.md)과 [작업표](incident-workflow-implementation-tracker.md)의 P1 구체안이다. 아래 명령·설정·상태 이름은 추가 구현할 인터페이스이며 지금 Slack에서 사용할 수 있는 기능이 아니다. 현행은 `investigate 대상 질문`만 지원한다.

## 1. 설계 결정

| 결정 | v1에서 채택할 설계 | 현재 적용 여부 |
| --- | --- | --- |
| D1 조사 시작 | 새 정책의 기본값 manual. 자동 조사는 명시적인 대상+경보명 허용 조합에서만 opt-in | 설계 선택 완료. 현행5종 자동조사 설정/코드는 변경하지 않음 |
| D2 채널 | 기존 경보 채널과 #ai-ops 유지. 사건 참조/ID로 연결하고 결과는 사용자의 요청 thread로 회신 | 사용자 확인한 현재 분리 유지. 연결 구현 예정 |
| 사건 모델 | 경보 발생 회차(event)와 기존 조사 결과 incident를 구분 | 신규 장부 예정, 기존 IncidentStore/큐 ID 변경 없음 |
| 사건 공지 | 기존 Slack 경보 전송 독립 유지. 공지에는 원인 추정 대신 사실과 사건 참조·조사 방법 표시 | 플랫폼 템플릿 구현/검증 예정 |
| 최초 범위 | 인증된 경보의 메타데이터 등록과 등록 대상의 읽기 조사 | 실행/복구/권한 확대 없음 |

D1/D2는 후속 로컬 구현 기준으로 채택한 설계다. 실제 자동조사 중단·신규 활성화·채널/권한 변경은 연결 계획에서 현재 설정과 전환 효과를 보여 주고 적용한다. D3 명령 승인 UI, D4 운영 실행/보관 기한, D5 최초 명령 대상은 이번 범위 밖의 미정이다.

## 2. 식별 계약

새 이벤트의 공개 ID는 `evt-` + SHA256 전체64자리 소문자 hex다. 내부 입력은 canonical JSON의 `schema_version=1, source_id, cluster_id, fingerprint, starts_at`이며 키 정렬/고정 JSON 인코딩 후 SHA256한다. `source_id`는 서버에 등록한 Alertmanager 논리 발신원(HA replica는 같은 값)이고 요청 본문이 임의 선택하지 못한다. `cluster_id`도 인증된 발신원 바인딩과 일치해야 한다.

`starts_at`은 기존 `alert_time`의 UTC 나노초9자리 정규화를 재사용한다. 순간이 같은 Z/offset·소수 자릿수 표기는 같은 ID가 된다. `fingerprint`는 기존16자리 소문자hex 규칙을 사용한다. 인증은 전제이며 ID/해시는 권한이나 무결성을 단독 증명하지 않는다.

| 식별자 | 의미 | 관계 |
| --- | --- | --- |
| `evt-…` | 특정 경보의 발생 회차 | 여러 조사 작업을 참조할 수 있음 |
| `job-…` | 기존 큐 조사 작업 | 새 이벤트-작업 연결 테이블로 evt와 연결 |
| `inc-…` / `run-…` | 기존 IncidentStore 분석 결과/실행 | 기존 의미·보관 규칙 유지; evt와 혼용 금지 |
| Slack event_id | 서명된 사용자 요청 이벤트 | 재전송 중복키의 근거, 경보 발생 ID가 아님 |
| `alert_ref` | 기존 경보 메시지에서 복사할 짧은 원본 참조 | 서버에서 canonical evt로 해석하며 권한 재검증 |

동일 발생키에 대해 alertname·정렬된 전체 labels의 해시·정규화한 등록 대상 식별을 불변 값으로 저장한다. 같은 키에 다른 labels/대상이 오면 overwrite나 재바인딩 대신 `identity_conflict`로 거절한다. 동적인 annotations는 ID나 명령에 사용하지 않고 공지에 필요한 정제/제한 길이의 사실만 저장한다. UID는 최초 조사 시 관측한 대상과 별도로 연결한다. 나중에 같은 이름의 workload가 재생성됐으면 자동으로 이전 사건과 동일 실물로 보지 않는다.

### 중복·재발·해제 규칙

- 동일 발신원/cluster/fingerprint/startsAt의 반복 firing: 같은 evt, 새 자동조사/공지 연계 작업 생성 금지. Alertmanager의 기존 반복 통지 정책은 유지.
- startsAt이 다른 동일 경보: 새 evt. 이전 조사·승인·복구 결과 재사용 금지.
- 서로 다른 경보명이 같은 원인을 가질 수 있어도 v1에서 자동 병합하지 않는다. 관련 사건 표시만 후속 기능으로 둔다.
- resolved가 먼저 오면 같은 evt의 해제 기록을 먼저 만들고 늦은 firing으로 다시 열지 않는다. 같은 묶음은 기존과 같이 resolved 우선 처리.
- firing의 endsAt은 해결 증거로 쓰지 않는다. resolved 상태와 유효한 endsAt을 확인해야 한다.
- 경보 해제는 조사 완료·사람 승인·복구 성공을 뜻하지 않는다. 자동조사 queued 상태에서 해제를 확인하면 새 수집 시작을 중지, 이미 읽기 조사중이면 결과에 해제/관측시각을 표시한다. 실행 취소/원복을 자동 호출하지 않는다.
- 없는 evt를 Slack 메시지만으로 생성하지 않는다. 신규 사건은 인증된 경보 접수 경로만 만들 수 있다.

## 3. 경보 등록과 조사 권한 분리

기존 `AlertInbox`는 허용5종의 조사 접수기다. 이 허용 목록을 풀어서 모든 경보를 조사시키지 않는다. 새 사건 접수 경로는 인증·본문 크기·잘림·발신원·라벨 형식·시각 검증을 유지하면서 메타데이터를 등록한다. 일반 경보에 앱 Target 필드가 없을 수 있으므로 raw identity와 `target_resolution=bound / unbound / conflict`를 별도로 둔다.

미등록 노드/서비스 경보는 `unbound`로 저장하고 공지는 유지하지만 조회 selector/URL/PromQL을 만들어 실행하지 않는다. 수집 가능한 등록 Target과 현재 요청자의 대상 권한이 확인돼야 조사한다. 누락 Target을 default namespace나 질문으로 추측하지 않는다. Watchdog는 기존 heartbeat 경로를 유지하고 기본적으로 사용자 장애 사건에 넣지 않는다. 억제된 경보는 Alertmanager가 전달하지 않을 수 있으므로 사건 장부가 모든 firing을 빠짐없이 포함한다고 주장하지 않는다.

## 4. 두 채널 연결 계약

경보 채널 ID는 아직 이 설계에서 실물 확인하지 않았다. 배포 전 현재 Webhook 목적지와 채널 ID를 확인한다. #ai-ops는 기존 조사 channel_id를 재사용한다. 채널명은 표시용이고 인가는 workspace/channel ID로 수행한다.

**기존 Alertmanager→Slack Webhook 경로를 그대로 유지**하고, 별도 인증된 경보 접수로 사건 장부를 채운다. 사건 서버 장애가 기존 Slack 공지를 차단하지 않는다. 두 경로 도착 순서는 보장되지 않으며 v1은 Slack 수신 확인을 조사 시작의 선행 조건으로 쓰지 않는다. 사용자에게는 항상 먼저 사실 공지를 내보내는 경로를 두고 분석 완료를 기다리지 않는다.

기존 Webhook 통지에서 새 서버 evt를 조회하거나 Slack message ts를 얻는다고 가정하지 않는다. 대신 경보 템플릿에 다음 `alert_ref`를 넣는다.

`al1/<source_alias>/<fingerprint>/<startsAt RFC3339>`

합성 예시: `al1/lab-seoul/0123456789abcdef/2026-11-18T12:00:00Z`

source_alias는 서버 발신원 설정과 대조하는 고정 값, fingerprint와 startsAt은 해당 개별 경보 값이다. 템플릿 시각은 전달 payload와 동일 순간·정밀도를 유지해야 한다. WF-03에서 실제 잠금된 Alertmanager 템플릿 fixture로 검증하고, 나노초 손실이나 서로 다른 source_alias가 발견되면 연결 완료로 처리하지 않는다. Template의 전달 형식은 검증 후 고정하며 여기서 동작을 검증했다고 주장하지 않는다.

수신기는 alert_ref를 파싱→등록 발신원/cluster 조회→시각 정규화→evt 계산→저장된 불변 값 대조 순서로 해석한다. 이때 경보 채널 메시지 URL은 없어도 된다. 원본 message ts/permalink는 선택 메타데이터이며 v1에서 Slack history 권한을 새로 요구하지 않는다. 사용자 제공 링크를 임의 HTTP로 조회하지 않는다.

공지 내용: 발생 대상·경보명·발생 시각·임계 초과 등 관측 사실·firing/resolved·alert_ref·#ai-ops 조사 예시. 비밀값/원문 로그를 공지에 넣지 않는다. 조회/설명할 수 없는 노드 대상에는 자동조사 가능이라고 표시하지 않는다.

### 제안 입력과 출력

새 입력: `@봇 investigate-event <alert_ref 또는 evt-ID> [질문]`.

기존 `@봇 investigate <등록별칭> [질문]`은 유지하되 사건 미지정 일반 조사로 표시한다. “이 장애”만 입력하면 channel/thread와 서버 사건 연결이 하나로 확정된 경우에만 해석하고, 그렇지 않으면 식별값을 요청한다. 질문에 복구 지시가 있어도 읽기 조사로만 처리한다.

서명→현재 사용자/채널 허용→참조 해석→사건 Target과 대상 권한 확인→영속 요청접수→기존 TaskService/JobQueue 전달 순서다. 알림 채널에서 명령을 보내면 기본 거절/조사 채널 안내만 하며 그 채널의 조사 권한을 자동 추가하지 않는다. 권한이 없는 사건의 존재/대상/상태를 오류 메시지로 노출하지 않는다.

응답: `조사 접수: evt-… / 작업 job-… / 경보발생 시각 / 실제 조사 범위`. 결과는 서명된 원래 요청의 channel/thread로만 돌아가며 evt·자료 시각·현재 상태·원인 후보·부족자료·런북 출처·job/inc/run을 포함한다. 모든 사용자 결과를 하나의 공용 thread로 합치지 않는다.

경보와 사건 접수의 순서가 뒤집혀 아직 evt가 없으면 `사건 접수 확인 중, 아직 조사 작업 없음`으로 반환한다. 요청이 승인된 조사로 큐에 들어갔다고 표시하지 않으며, bounded 재조회 기능을 후속 구현하거나 사용자가 다시 요청할 수 있게 한다. 새 경보를 사용자 입력으로 합성하지 않는다.

## 5. 조사 시작 정책 v1

설정에는 정책 schema_version·policy_revision, workspace/source/channel 바인딩, 대상별 manual/automatic 예외를 둔다. 예시 의미는 `default=manual`, `automatic_rules=[]`다. runtime 설정 파일 형식/스키마 구현은 WF-02에서 정하며 현재 설정을 덮어쓰지 않는다.

자동 예외의 키는 정확한 source+cluster+등록 target+alertname이다. wildcards로 범위를 늘리지 않는다. enabled=true뿐 아니라 기존 허용5종·ai_ops=enabled·firing·최신 등록 설정과 권한 검증이 필요하다. 자동 예외에는 결과를 받을 등록 channel/고정 audience 정책도 필요하다. 자동 조사 결과의 전달까지 준비되지 않으면 새 자동 예외 활성화를 거절한다. 해당 채널 통합은 기존 사용자 요청 thread 회신과 별도 WF-03/04 작업이다.

| 입력·상태 | 사건 접수 | 조사 시작/결과 |
| --- | --- | --- |
| 신규 경보, manual | 등록 | 공지 경로 유지, 사용자 요청 전 큐 작업0 |
| 신규 경보, 정확한 automatic 예외와 모든조건 충족 | 등록 | 사건당 자동 작업1개 예약, 정책·대상 재검증 후 기존 큐 전달 |
| 자동 예외 있으나5종외/라벨없음/대상미등록 | 등록 또는 identity conflict 거절 | 큐0, 범위 밖으로 기록 |
| 허용 사용자 명시 조사, bound 사건 | 기존 사건 조회 | 경보명이5종 밖이어도 등록 수집 대상/지원 자료 범위 내 읽기 조사 가능; 원인 확정 보장 없음 |
| 허용 사용자 명시 조사, resolved 사건 | 기존 사건 조회 | 과거 장애 조사임을 표시하고 발생 당시 보존 자료와 현재 수집을 구분 |
| 미허용 사용자/채널/대상 | 외부 요청으로 사건 생성0 | 정보 노출 없이 거절, 큐0 |
| 중복 Slack event_id | 기존 접수 반환 | 같은 요청/작업 유지, 큐 중복0 |
| 자동 조사 수행 중 같은 사건의 사용자 요청 | 기존 작업 검사 | 사용자 권한·목적·설정이 동일한 기본 조사일 때만 연결. 질문이 다르면 별도 작업, 무한 병렬은 기존 admission 한도 적용 |
| 오래된 결과 존재 | 기존 참조 | 시각·설정·대상 유효성 미확정이면 새 조사. silent 재사용 금지 |
| 정책 manual로 바뀐 뒤 미전달 자동 요청 | 사건 유지 | 실행 직전 revision 확인으로 중지. 진행중 읽기 결과는 자동 실행 승인으로 승격하지 않음 |

v1에서 완료된 과거 조사 결과는 이력으로 보여 주고 사용자 새 요청의 현재 조사 결과로 자동 대체하지 않는다. 최신성 재사용 정책은 후속 계약이 검증된 뒤 추가한다. 자동 작업1개는 사건/목적 키에 unique 제약을 두고 outbox→기존 queue의 안정 request_id를 사용해 재시작 중복을 막는다. 자동 실패의 무제한 재생성 대신 실패 상태와 수동 재조사 경로를 제공한다.

정책 변경은 과거 경보를 일괄 자동 조사시키지 않는다. 활성화 이후 신규 회차부터 적용하며, 기존 큐/worker를 비우거나 기존 조사 결과를 삭제하지 않는다. 기존 alert_episodes.job_id와 새 evt 매핑은 마이그레이션에서 보존하고 불일치 시 자동변환을 중지한다. queued 자동작업의 시작점에서 policy_revision 재확인 구현이 필요하다.

## 6. 저장 데이터·상태 경계

WF-02 산출물은 events(불변 identity/시각/상태/Target resolution), event_requests(사용자/정책/질문 정제 참조), event_jobs(evt↔job, source/manual/automatic), outbox(목적/중복키/전달상태), source_alias 설정과 마이그레이션이다. 기존 IncidentStore·JobQueue 테이블을 다른 의미로 재사용하지 않고 연결 테이블로 확장한다. 중복 접수와 outbox 예약은 같은 로컬 트랜잭션으로 처리하고 큐 접수 ACK와 조사 완료를 구분한다.

공지 전송 상태는 `unknown`이 기본이다. 사건 webhook 수신만으로 기존 Slack 알림이 delivered라고 기록하지 않는다. 기존 Slack API 회신의 delivered 역시 API 수락이며 사용자 읽음/실행 승인이 아니다.

장부는 기존 사용자전용 파일/SQLite 보호를 따른다. source/Target 메타데이터와 정제 사실만 보존하며 raw Slack 질문/토큰/경보 원문 전체를 복제하지 않는다. 기존 조사·Slack 보관7일을 확대하지 않는다. 새 사건 장부의 상세 보관·tombstone/active 사건 처리·용량은 WF-02에서 정책으로 확정하고, 만료 시 오래된 사건 요청을 새 사건으로 조용히 재생성하지 않는다. 전체 실행/승인 대기 기한(D4)과 장부 보관은 별도다.

## 8. 다음 작업과 보존 조건
