# WF-09 효과검증·원복/수동 인계 로컬 계약 · 2026-11-19

## 이유와 범위

R5/R6에 따라 사람 승인 대기, 변경 적용, 효과 관찰, 후속 조치, 회수를 분리한다. PR 병합·Argo 적용·명령 종료·경보 해제는 서비스 회복 증거를 대신하지 않는다. WF07/08 main `6891144c6c31e29a856d701191c9eb177764204a`에서 `codex/wf09-effect-verification-20261119`로 분기해 로컬 구현했다.

`recovery_effects.py`는 기존 개인 JobQueue SQLite에 같은 사건/job/계획의 효과 결과·후속 후보·회수 상태를 저장한다. 새 조사 큐/worker나 운영 권한을 만들지 않는다. 현재 코드 미커밋·CI/main 미반영이다. 아래 포트와 표본은 합성 로컬 계약이며 실환경 회복·정리 완료로 해석하지 않는다.

## 기존 경로와 연결

- WF07 `record_sync`가 기존 정확 head 리뷰/CI·병합·동기화 검증을 통과한 관측 시각을 보존한다. `pr_effect_source`는 원래 계획/사용자/근거의 인가·보관을 다시 확인하고 같은 DB의 적용 결과를 읽는다. PR을 만들거나 GitHub에 요청하지 않는다.
- WF08은 적용 확인의 최초 관측 시각을 보존한다. `command_effect_source`는 봉인된 RestartPlan·원래 감사 근거·image·실행 장부를 대조한다. 정상 효과는 같은 Deployment UID/semantic revision·image·restart marker·다음 generation과 **이전 Pod와 다른 새 Pod**를 요구한다.
- 경보 해제 후 효과 결과 조회를 허용하는 `for_effects` 접근자를 기존 명령 source와 분리했다. 기존 실행 loader는 여전히 firing 사건을 요구한다. 해제는 실행 승인도, 자동 성공도 아니다. 원래 요청자·현재 Slack 정책/대상·자료 보관 검사는 두 경로에서 유지한다.
- 이전 버전의 적용 기록에 시각이 없으면 시간을 새로 만들어 주지 않고 검증불가다. 이미 봉인한 효과 장부와 적용 결과가 바뀌면 기존 결과를 새 실행에 재사용하지 않는다.

## 효과 판정

정책의 시작/종료·표본/간격·지표식 hash/기준값·경보 규칙 hash·보고 신선도·읽기 예산은 필수 입력이다. 합성 시험은 관찰120초·30초 간격5표본을 사용한다. 일반 운영의 새 기본 시간이나 SLO를 정한 것은 아니다. 기존 C04 정책 파일은 수정하지 않았다.

- 최소 관찰120초, 최소4표본, 최대 간격45초, 최대 보고 지연120초, 읽기 예산15초 이내로 제한한다. 실제 수집 시각·적용 이후 관찰 창·UID·정확 실행 hash·조회 정의가 맞아야 한다.
- 필수 항목은 runtime, `/readyz`, `/items`의 HTTP200+본문 계약, 정책의 지표 및 경보 규칙이다. 기존 C검증의 HTTP/지표/경보 자료형과 항목 판정 함수를 재사용한다. 빈 값·누락 exporter·존재하지 않는 경보 규칙을0/정상으로 채우지 않는다.
- PR은 적용 commit·Application UID·고정 digest·Argo Synced/Healthy·관측 generation·한 Pod의 Ready를 요구한다. 명령은 원래 semantic revision/image와 소유 marker·교체 generation·새 Pod를 확인한다.
- 모든 필수 자료가 관찰 구간 전체에서 통과하면 `succeeded`; 확인된 불일치가 하나라도 있으면 `unresolved`; 충분하지 않거나 출처/대상/시각이 다르면 `verification_unknown`이다. 자료 부족과 확인된 실패가 동시에 있으면 실패를 숨기지 않되 자동 후속 후보는 막는다.
- 같은 계획·정책·적용 결과·회수 manifest로 재시작해도 같은 장부를 읽는다. 다른 정책/대상/실행으로 조용히 갱신하거나 기한을 연장하지 않는다. 결과는 한 번 기록하며 새 관찰을 기존 실패 덮어쓰기로 사용하지 않는다.
- 취소/병렬 처리 중 세대가 바뀌면 늦은 결과가 취소를 덮어쓰지 않는다. 최초 실패와 현재 효과·취소는 분리 보존한다. `service_resolved`는 합성 자료의 판정이며 실제 서비스 완료 주장이 아니다.

## 원복 후보와 수동 인계

재시작은 이전 프로세스로 돌아갈 수 없다. 명령이 미해결/불명확하면 `manual_handoff`로 남기며 같은 명령·이미지 변경을 추가 실행하지 않는다.

PR도 실패만으로 자동 Git revert나 다른 digest 선택을 하지 않는다. 완전하고 신선한 미해결 근거가 있고, 신뢰된 승인 조회 포트의 `RollbackScope`가 같은 실행 hash·Deployment/Application UID·사전 승인 hash·검증 기준선 hash·정확 revision/digest·기한·미소비1회를 만족할 때에만 `rollback_candidate`를 저장한다. 범위가 없거나 만료/취소/다른 대상이면 새 승인 요청 또는 수동 인계다. 승인 뒤 최신 원본·권한·잠금·기한 재검증은 기존 실행 경로가 다시 수행해야 한다.

`RollbackScope` 모델/해시는 승인 진위를 증명하지 않는다. 이 단계는 내부 신뢰 포트/로컬 fixture 계약이며 Slack 사용자 JSON으로 scope를 받는 승인 API가 없다. 원복 후보의 `execution_allowed=false`와 `requires_execution_revalidation=true`를 유지한다. WF09 자체에 Git revert/merge/sync writer는 없다.

`record_rollback_local`은 별도로 적용된 정확 원복의 합성 receipt·동일 검증 정책·새 관찰 창을 검사한다. 원래 실패와 원복 결과를 다른 필드로 저장하고, 한 번 확인을 시작한 뒤 불확실한 결과를 자동 재시도하지 않는다. 원복 정상은 `rollback_verified`지만 `first_result`는 최초 미해결 그대로다. 잘못된 원복·미승인·자료 부족은 수동 인계로 남긴다.

## 자기 자격·잠금·임시 자원 회수

허용 목록은 신뢰된 실행 소유자가 만든 `CleanupItem` manifest다. 항목은 종류·소유자 hash·리소스 hash·고정 행동만 담고 토큰·원문 응답을 저장하지 않는다. 원래 적용 기록에 미회수 Lease가 있으면 manifest에서 빠뜨릴 수 없다. 항목 전체 hash를 봉인해 이후 목록을 바꿔 회수 완료로 만들지 않는다.

- 종류별 행동은 `release_lease`, `revoke_credential`, `remove_temporary`다. 임의 명령/URL은 받지 않는다. 기존 operator/로그인/App 키/Slack 원본 자격은 이 manifest가 다룰 대상이 아니다.
- `local_fixture` 포트만 실행한다. 먼저 동일 소유를 조회하고 장부에 시도를 예약한 뒤 자기 항목만 처리한다. 실제 포트 연결 시 dispose는 소유자 조건을 원자적으로 검사해야 한다. mode 문자열 자체가 악성 코드를 격리하는 장치는 아니다.
- 응답 유실/프로세스 종료 뒤에는 조회로만 조정한다. 재시도 버튼으로 회수 쓰기를 중복하지 않는다. 소유자가 다르거나 실제 부재가 확인되지 않으면 완료라고 표시하지 않는다. Lease 호출별 deadline은 기존3초와 전체 남은 예산 중 작은 값이다.
- 효과 성공과 회수 완료는 별개다. `cleanup_complete`는 `cleanup_scope=declared_owned_manifest_only`에 한정한다. 외부 자원 전체 재고 조사나 실제 Secret/Lease 회수 검증을 수행했다는 뜻이 아니다. 실제 자격 발급자의 정리 manifest/소유권 포트는 후속 구현이다.
- 보관 만료 때 사건/job·표본 판정/회수 metadata를 지우고 최소 hash/종료 표식만 남긴다. 원본 큐/조사/다른 장부는 삭제하지 않는다. 종료 표식 포함 상한1만개와 항목16개 제한이 있다. 주기 prune 연결은 배포 전 작업이다.
