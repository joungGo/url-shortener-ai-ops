# C-04 로컬 감시 Lease timeout 재현·계측 보완

## 결론

실제 202611180002 기록은 로컬 감시의 Lease GET이 응답 헤더 대기 중 3.001316초에 실패하고 종료됐음을 보여준다. 실제 인증/DNS/TCP/TLS/API 중 지연 원인은 아직 미확정이다. 장애 실습은 반복하지 않았으며 이 결과를 원인 해결이나 실행 준비 완료로 사용하지 않는다.

로컬에서 정상 조회 후 3초 동안 헤더를 보내지 않는 Unix 서버로 같은 감시 종료를 재현했다. 기존 하위 계측 코드는 main에 있었지만 실제 감시 CLI에서 옵션을 전달할 경로가 없었다. 또한 종료된 감시는 이전 standby marker를 남기고, 부모의 RefreshingProbe가 성공 증거를 폐기하면서 최종 결과에는 원래 Lease 오류가 전달되지 않았다. 이 두 관측/진단 결함을 수정했다. 네트워크 timeout 자체를 없앴다는 의미는 아니다.

## 수정

- 감시 CLI에 `--lease-trace-binary`와 `--lease-trace-sha256` 쌍을 추가했다. 기존 소유자/권한/절대경로/상위경로/바이너리 해시 검사로 고정한다. 기본값은 기존 kubectl이고 환경변수로 자동 활성화하지 않는다. 실행 중 다운로드·빌드는 없다.
- LeaseRequestError로 종료할 때 marker 옆 `.failure.json`에 같은 intent/guard/role의 정제된 실패를 한 번만 원자적으로 기록한다. 기존 marker는 덮어쓰지 않는다. 기록 실패여도 원래 오류·중지·정리 경로를 유지한다.
- 부모는 실패 기록의 연결 대상을 먼저 대조하고 성공 캐시를 폐기한다. 죽은 PID 때문에 원래 사유가 가려지지 않도록 실패 정보를 먼저 읽으며 최종 결과의 `local_guard_failure`에 전달한다. 파일만으로 감시가 정상이라는 판정을 내리지 않는다.
- 고정 code/method/phase/cause, 제한된 경과시간·HTTP status, 마지막 관측 단계만 재검증해 전달한다. 예외 원문·본문·헤더·자격·주소·파일 경로는 넣지 않는다. 단계 이력은 best effort이며 마지막 단계가 확정 원인이라는 주장을 하지 않는다.

## 로컬 검증

- 전체 Python 시험 **1,257개 통과**, 신규 **10개**: 실제 Unix 헤더 지연, 추적 옵션 전달, 원래 예외 보존/정리, 쌍이 없는 옵션 거절, SIGTERM 유지, 실패 후 캐시 폐기, 죽은 PID에서도 진단 보존, 다른 intent/guard/role 거절, 비밀값 제거/요약 재검증, 초대형 정수의 진단 OverflowError 방지.
- 가짜 exec 인증과 localhost TLS를 사용하는 기존 단계 검사 3개 통과. 인증·TLS·응답 대기 지연은 모두 외부에서는 `response_headers/timeout`으로 나타났다. 상세 이력은 각각 `authentication`, `tls`, `response_wait` 시작을 구분했다. 약3.001초에 각각 중지했고 실제 cloud 호출0, 비밀 canary 미출력, proxy/socket/reader 회수 확인.
- 현 소스/잠금/해시와 일치하는 기존 v0.35.8 계측 바이너리를 재사용했다. 먼저 확인한 이전 보존 빌드는 현 소스 해시와 달라 실행하지 않았다.
- 조회3초·시작15초·안내후 리뷰최소120초/시작후210초·소유원복240초/독립원복300초·관찰120초 유지. 제어기/감시루프/원복/RefreshingProbe의 소스가 base와 동일함을 대조했다. 재시도·PUT 재전송·실패 캐시 사용·승인/UID/CAS/ACK 완화 없음.

검증 수치·변경 파일 해시는 [JSON](C4-lease-timeout-local-20261118.json)에 있다. 개인 로그는 `~/.local/share/url-shortener-ai-ops/c04-lease-timeout-local-20261118/`에 보관한다. pytest가 아니라 저장소의 unittest suite로 검증했으며 클라우드/API/Slack·실제 배포·실습은 실행하지 않았다.
