## 변경

준비 완료 실행에서 각 읽기 구간의 감시·이미지·리소스 snapshot을3개 worker로 함께 읽는다. 첫 구간을 모두 완료·검증한 뒤 두 번째 구간을 시작한다. snapshot 안의 전후 UID/spec 대조 barrier도 그대로다. 두 번째 구간 종료·검증 이후 소유 Lease·activation과 양쪽 guard ID/ACK를 **새로 읽고** 첫 쓰기로 넘어간다. 조회를 캐시로 대체하거나 검사를 생략하지 않는다. 예외는 남은 읽기 종료 뒤 전파하며 앱을 변경하지 않는다. 이전 달력 실행 경로의 순서는 바꾸지 않았다.

`StartupTrace`가 승인 재검사·승인 소비/fsync·Lease 취득·감시 연결/ACK·각 snapshot/이미지/감시 읽기·최종 ACK·쓰기 journal·시각 검사의 단계 이름/상태/소요 시간만 기록한다. `elapsed_ms`는 승인 처리 전체, `critical_elapsed_ms`는 T를 고정한 경계부터 첫 쓰기 직전까지의 참고 계측이다. 실제 허용 판단은 기존 UTC/monotonic 검사로 수행한다. 진단 자체가 시간을 소모한 경우도 최종15초 검사에서 차단한다.

오류 본문/요청/CLI 인자/응답/자격은 받지 않으며 event는최대128개다. 최초 쓰기 후보 또는 주입 전 거절 때 기록을 고정한다. 실행기는 결과 JSON의 `startup_timing`과 개인 `startup-timing.json`을 남긴다. 진단 파일 저장 오류가 포워드·소켓·감시 정리를 건너뛰지 않도록 정리 뒤에 저장한다. 진단 시간만으로 실제 쓰기 성공을 판정하지 않는다.
